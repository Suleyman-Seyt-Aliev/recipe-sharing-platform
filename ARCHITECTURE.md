# Архитектура платформы для шеринга рецептов и планирования меню (Вариант 24)

## 1. Назначение системы
Платформа позволяет кулинарам публиковать рецепты, а шеф-редакторам — модерировать их. Ключевая функция: автоматический пересчёт ингредиентов при изменении количества порций и формирование общего списка покупок на выбранные блюда.

## 2. Ролевая модель и Use Cases

**Роли пользователей:**
* **Кулинар (Author)** — создаёт и управляет своими рецептами.
* **Шеф-редактор (Editor)** — проверяет и публикует рецепты.

**Сценарии использования (Use Cases):**

**Кулинар:**
* Регистрация / Вход в систему.
* Создание нового рецепта (название, описание, фото, категория).
* Добавление ингредиентов с указанием количества.
* Редактирование и удаление своих рецептов.
* Просмотр списка своих рецептов.

**Шеф-редактор:**
* Вход в систему.
* Просмотр рецептов, ожидающих модерации (статус "На проверке").
* Публикация рецепта (статус "Опубликован").
* Отклонение рецепта с указанием причины.

**Система (общие функции):**
* Изменение количества порций в рецепте с автоматическим пересчётом ингредиентов.
* Генерация сводного списка покупок по выбранным рецептам.

## 3. C4 Модель (Уровень Container)

На схеме показаны основные контейнеры системы и их взаимодействие.

```mermaid
graph TD
    User[Пользователь / Браузер] -->|HTTP / HTTPS| Frontend[Веб-интерфейс]
    
    subgraph Backend[Серверное приложение]
        API[API Gateway / Web API] --> BL[Слой Бизнес-логики]
        BL --> Cache[Redis / Кеш]
        BL --> DB[PostgreSQL / БД]
    end

    Frontend -->|Вызов REST API| API
    API -->|Чтение и запись| DB
    BL -->|Кеширование списков| Cache
Описание компонентов:

Веб-интерфейс — клиентская часть (браузер пользователя).

API Gateway — принимает запросы от пользователей и направляет их в бизнес-логику.

Слой Бизнес-логики — выполняет расчёты порций, управляет модерацией и генерацией списков.

PostgreSQL — основное реляционное хранилище всех данных (пользователи, рецепты, ингредиенты).

Redis — кеш-хранилище для быстрых расчётов списков покупок, чтобы не пересчитывать тяжелые запросы каждый раз.

4. ER-диаграмма (Схема базы данных)
Список сущностей (таблиц):
Всего в базе данных будет 6 таблиц:

users — пользователи системы.

categories — категории рецептов.

ingredients — справочник всех ингредиентов (молоко, мука, соль).

recipes — сами рецепты.

recipe_ingredients — состав рецепта (связывает рецепты и ингредиенты).

shopping_lists — сгенерированные списки покупок для пользователей.

Структура таблиц (описание полей):
Таблица 1: users (Пользователи)

Название поля	Тип данных	Ограничения	Что хранит
id	UUID	PRIMARY KEY	Уникальный номер пользователя
email	VARCHAR(255)	NOT NULL, UNIQUE	Почта для входа
password_hash	VARCHAR(255)	NOT NULL	Зашифрованный пароль
role	VARCHAR(20)	CHECK (role IN ('author','editor'))	Роль (Кулинар или Редактор)
Таблица 2: categories (Категории блюд)

Название поля	Тип данных	Ограничения	Что хранит
id	BIGINT	PRIMARY KEY	Номер категории
name	VARCHAR(100)	NOT NULL, UNIQUE	Название (например, "Супы")
Таблица 3: ingredients (Справочник продуктов)

Название поля	Тип данных	Ограничения	Что хранит
id	BIGINT	PRIMARY KEY	Номер продукта
name	VARCHAR(150)	NOT NULL, UNIQUE	Название (например, "Мука")
unit	VARCHAR(20)	NOT NULL	Единица измерения (г, мл, шт)
Таблица 4: recipes (Рецепты)

Название поля	Тип данных	Ограничения	Что хранит
id	BIGINT	PRIMARY KEY	Номер рецепта
title	VARCHAR(200)	NOT NULL	Название блюда
description	TEXT	-	Шаги приготовления
cooking_time	INT	-	Время готовки в минутах
servings_base	INT	NOT NULL DEFAULT 1	На сколько порций рассчитан рецепт
status	VARCHAR(20)	CHECK (status IN ('draft','pending','published','rejected'))	Статус модерации
author_id	UUID	FOREIGN KEY (ссылка на users.id)	Кто создал рецепт
moderator_id	UUID	FOREIGN KEY (ссылка на users.id)	Кто проверил рецепт
category_id	BIGINT	FOREIGN KEY (ссылка на categories.id)	К какой категории относится
Таблица 5: recipe_ingredients (Состав рецепта — связующая таблица)

Название поля	Тип данных	Ограничения	Что хранит
recipe_id	BIGINT	PRIMARY KEY, FOREIGN KEY (ссылка на recipes.id)	Какой рецепт
ingredient_id	BIGINT	PRIMARY KEY, FOREIGN KEY (ссылка на ingredients.id)	Какой ингредиент
quantity	DECIMAL(10,2)	NOT NULL	Количество на 1 базовую порцию
Таблица 6: shopping_lists (Списки покупок)

Название поля	Тип данных	Ограничения	Что хранит
id	BIGINT	PRIMARY KEY	Номер списка
user_id	UUID	FOREIGN KEY (ссылка на users.id)	Кто создал список
recipe_ids	JSONB	-	Массив ID выбранных рецептов
total_servings	INT	NOT NULL	Желаемое количество порций
created_at	TIMESTAMP	DEFAULT NOW()	Дата создания
Типы связей между таблицами (ER-связи):
users (1) → recipes (N): Один кулинар может написать много рецептов. Связь реализована через поле author_id.

categories (1) → recipes (N): Одна категория (например, "Завтраки") может включать много рецептов. Связь через category_id.

recipes (1) → recipe_ingredients (N): Один рецепт состоит из множества строк ингредиентов.

ingredients (1) → recipe_ingredients (N): Один ингредиент (например, "Соль") используется во многих рецептах.

recipes (N) ↔ ingredients (M): Это связь "многие-ко-многим", которая реализована через промежуточную таблицу recipe_ingredients.
